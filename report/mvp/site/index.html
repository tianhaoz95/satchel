Satchel: an agent-neutral vault for personal records

Your records stay in your own folders. Any MCP agent can search them, file new ones and remind you before they expire. A thin relay makes your node reachable without ever reading your traffic, and your phone is the second factor for anything sensitive.

    What's on disk

    The vault stays a normal folder a person can browse. Everything Satchel adds is plain text and travels with the files:

    # your folder (NAS share, local, or Drive-synced)
Records/
├── VAULT.md                  ← agent instructions (policy as text)
├── .satchel/journal.jsonl       ← append-only change history (undo)
├── People/Alex/ID/
│   ├── 2024-05 Driver License (exp 2032-05).pdf
│   └── .2024-05 Driver License (exp 2032-05).pdf.satchel.yaml
├── Vehicles/2019 Honda Civic/Registration/
│   └── 2026-03 Registration (exp 2027-03).pdf
└── Inbox/                    ← phone captures land here

# node data dir (never inside the vault)
~/Library/Application Support/Satchel/
├── config.json               ← roots, security policy, relay
├── satchel.sqlite               ← index cache, tokens (hashed), approvals, audit
├── text/<sha256>.txt         ← extracted / OCR text cache
└── tls/key.pem               ← node's TLS key: never leaves
    # .2024-05 Driver License (exp 2032-05).pdf.satchel.yaml
# Satchel metadata. Plain YAML: edit it by hand if you like.
doc_type: drivers_license
subject: Alex
title: California Driver License
issued_on: 2024-05-14
expires_on: 2032-05-14
license_number: D7741025   ← masked for agents: D774••••
sensitive: [license_number]

    Design rule from our discussion: the node is dumb on purpose. It stores facts, enforces permissions and journals changes. Naming, layout and reminder habits live in VAULT.md, which smarter agents can use more fully. Security policy is the exception: it lives in config.json, out of agents' reach.

    MCP tools

    ToolScopeWhat it does

    Security model

    PartySeesNever sees
    Your nodeEverything–
    Relay operatorSubdomain (SNI), timing, byte countsRequests, responses, tokens, files
    Portal / SupabaseGitHub login, subdomain, token hash, online flagAnything in the vault
    Model providerTool results: masked metadata, redacted text, approved valuesMasked values, delivered values
    Push serviceThat a notification firedContent (encrypted, and contains no values)
    • TLS passthrough. The node holds the key; the relay splices ciphertext. Verified in the e2e test, which checks that the certificate seen through the relay is the node's.
    • OAuth on the node. The consent page, password check and token issuance run locally, so the relay operator can't mint access.
    • Masking that only tightens. Agents can add sensitive keys, never remove them. Masked values are kept out of the search index.
    • Redaction. Known sensitive values are removed from document text (best effort).
    • Deliver, don't reveal. deliver_to_user sends a value to your phone; the model never sees it.
    • Approvals show facts first. The agent's reason is labeled "unverified". Revealed values can be picked up once.
    • Audit. Per agent, which sensitive values it actually received.
    • Path safety. No escaping roots; .satchel/ and sidecars are unreachable through tools.

    Decisions to review

    • Name Satchel, the GitHub org satchel-dev and the satchel.dev domain are placeholders
    • Phone app is a PWA served by the node rather than a native app: zero app-store friction, but iOS Web Push requires adding it to the Home Screen
    • Relay runs on a VPS, not Cloudflare (Pages/Workers can't do raw TCP passthrough)
    • OAuth consent uses the owner password; phone-approval as a consent option is a natural next step
    • LICENSE is the Apache-2.0 notice; add the full text before publishing
