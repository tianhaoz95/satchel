Init setup

What you need to provide to bring Satchel online

The code is done. Before the hosted parts can run, you need a domain on Cloudflare, a Supabase project, a GitHub OAuth app for sign-in, and a small server for the relay. This page walks through each one in order. Commands and URLs fill in from the values you enter below.

Nothing here is required to use Satchel locally. The node, desktop app and local agents work without any of this. These steps are only for the hosted relay address (you.) and the portal at .

Your values

Only non-secret identifiers go here. They stay in this browser (localStorage) and are used to fill in the commands on this page.

Where every value goes

Hover a source to trace it. secret values must only ever go to the places shown; never into the web build, a GitHub variable, or a commit.

1Put the domain on Cloudflare

  1. Buy (or use one you own). satchel.dev is only a placeholder in the code.
  2. In Cloudflare: Add a domain, choose the Free plan, and switch the nameservers at your registrar to the two Cloudflare shows you. Wait until the zone is Active.
  3. From the zone's Overview page, note the Zone ID and Account ID (right column). Neither is a secret.

2Create the Supabase project

  1. New project at supabase.com. Pick a region near your relay server. Generate a strong database password and store it in your password manager: it becomes the SUPABASE_DB_PASSWORD secret.
  2. Copy the project ref (the part before .supabase.co in the project URL) into Your values.
  3. Project Settings → API keys: note the publishable key (older projects call it anon; it's public by design and protected by RLS) and the secret key (older: service_role). The secret key bypasses RLS: it goes only to the relay server.
  4. Account → Access Tokens: create a token named github-actions. It becomes the SUPABASE_ACCESS_TOKEN secret, so CI can run supabase db push.

Project URL: https://.supabase.co

3Create the GitHub OAuth app (portal sign-in)

The portal signs people in with GitHub only, so there are no emails to send and no SMTP to set up. GitHub sign-in needs an OAuth app that sends users back to Supabase, not to your site.

  1. GitHub → Settings → Developer settings → OAuth Apps → New OAuth App. Use an organization if you have one, so the app isn't tied to a personal account.
  2. Fill in:
    Application nameSatchel
    Homepage URLhttps://
    Authorization callback URLhttps://.supabase.co/auth/v1/callback
  3. Generate a new client secret. Copy the Client ID and Client secret. You'll paste them into Supabase in the next step and nowhere else.

4Configure Supabase Auth

  1. Authentication → Sign In / Providers → GitHub: enable it and paste the Client ID and Client secret from step 3.
  2. Authentication → URL Configuration:
    Site URLhttps://
    Redirect URLshttps:///portal
    https://*..pages.dev/** (PR previews)
    http://localhost:5180/portal (local dev)
  3. Authentication → Sign In / Providers → Email: turn it off (it's on by default). With email disabled, GitHub is the only way to create an account, and you never need an email sender.

5Cloudflare Pages for the web app

  1. My Profile → API Tokens → Create Token → Custom token named satchel-pages-deploy. Permission: Account · Cloudflare Pages · Edit, limited to your account. This becomes CLOUDFLARE_API_TOKEN in GitHub.
  2. Create the Pages project once (CI deploys into it but doesn't create it): 
    npx wrangler login
npx wrangler pages project create  --production-branch main
  3. After the first deploy (step 8): Pages project → Custom domains → Set up a domain → . Cloudflare adds the DNS record itself (proxied, orange cloud, which is right for the website).

The VITE_* values are baked in at build time by GitHub Actions, so you don't need to set any environment variables on the Pages project.

6Relay server

The relay must accept raw TLS on port 443 and pass it through untouched, which Cloudflare Pages and Workers can't do, so it runs on a small VPS (1 vCPU / 1 GB is plenty to start). Any provider with a public IPv4 works: Hetzner, DigitalOcean, Fly.io machines, Lightsail…

  1. Create a VPS (Ubuntu 24.04), install Docker, and put its IP in Your values. Open inbound 443 and 7443 (plus 22 for SSH).
  2. Cloudflare DNS for : add these records as DNS only (grey cloud). If they're proxied, Cloudflare terminates TLS and breaks the end-to-end guarantee.
    TypeNameContentProxy
    ArelayDNS only
    A*DNS only
    The wildcard gives every node name.. Explicit records (the apex for Pages, relay) take precedence over it.
  3. A second Cloudflare token, satchel-relay-dns: Zone · DNS · Edit, limited to this zone only. The relay uses it to publish ACME TXT records so nodes can get real certificates for their own keys. It's also used once by certbot below.
  4. Get the relay's own certificate (for relay. only; node certificates stay on the nodes): 
    sudo apt install -y certbot python3-certbot-dns-cloudflare
sudo install -d -m 700 /root/.secrets
echo "dns_cloudflare_api_token = PASTE_DNS_TOKEN" | sudo tee /root/.secrets/cloudflare.ini >/dev/null
sudo chmod 600 /root/.secrets/cloudflare.ini
sudo certbot certonly --dns-cloudflare --dns-cloudflare-credentials /root/.secrets/cloudflare.ini \
  -d relay. --deploy-hook "docker restart satchel-relay-relay-1 || true"
  5. Create /opt/satchel-relay/compose.yml and /opt/satchel-relay/.env: 
    
          
    sudo install -d -o  /opt/satchel-relay
cd /opt/satchel-relay
cat > .env <<'ENV'
SUPABASE_SERVICE_ROLE_KEY=PASTE_SUPABASE_SECRET_KEY
CLOUDFLARE_ZONE_ID=PASTE_ZONE_ID
CLOUDFLARE_API_TOKEN=PASTE_DNS_TOKEN
ENV
chmod 600 .env
    6. 
        
  6. A deploy key for GitHub Actions: on your machine run ssh-keygen -t ed25519 -f satchel-relay-deploy -N "", append satchel-relay-deploy.pub to ~/.ssh/authorized_keys on the VPS, and keep the private key for step 7. Add the user to the docker group.

8Deploy and verify

      
    
        
  1. Apply the database schema: gh workflow run supabase.yml, then check that the nodes table exists in the Supabase table editor.
    2. 
        
  2. Deploy the site: gh workflow run web.yml (or push to main). Then attach the custom domain (step 5c) and open https://.
    3. 
        
  3. Publish the images: git tag v0.1.0 && git push --tags. When Container images finishes, make the two packages public (GitHub → your profile → Packages → satchel-node / satchel-relay → Package settings → Change visibility) so the VPS and NAS users can pull them without logging in.
    4. 
        
  4. Deploy hosted relay runs after the images; or start it by hand on the VPS: cd /opt/satchel-relay && docker compose up -d. Check: curl https://relay./healthz → {"ok":true}.
    5. 
        
  5. End to end: sign in on the portal with GitHub, create a node, then on your machine:
          
    node packages/node/src/cli.ts connect --relay relay.:7443 --token satchel_node_…
node packages/node/src/cli.ts serve
    
          The portal should show the node online, and https://NAME./mcp should answer 401 with OAuth metadata.
    6. 
        
  6. Connect a real cloud agent: add https://NAME./mcp as a custom connector in Claude, complete the consent page, and ask "what's expiring?".

Good to know

      
    
        
  • Rotating secrets: rerun the matching gh secret set; for relay values, edit /opt/satchel-relay/.env and run docker compose up -d.
    • 
        
  • Previews: each PR gets a Pages preview at *..pages.dev; the wildcard redirect URL from step 4 lets sign-in work there.
    • 
        
  • Costs at small scale: Cloudflare Free, Supabase Free (pauses after a week of inactivity; upgrade to Pro for production), one small VPS, and the domain.
    • 
        
  • Self-hosters need none of this: they run their own relay with a nodes.json file (see /docs/self-hosting).
